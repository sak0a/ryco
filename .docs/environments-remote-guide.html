Environments, remote machines & workspaces in Ryco

Everything hinges on one sentence: an environment is one running Ryco server. Local or on a remote PC, the client always speaks the same protocol to it — and that single boundary explains providers, worktrees, chats, pairing, Tailscale and updates all at once.

01The one big idea

Ryco has a clean runtime boundary. The client (a desktop Electron renderer, a browser tab on app.ryco.dev, or a phone) talks to a Ryco server over HTTP + WebSocket. That server owns everything real:

provider sessions & auth projects & threads git worktrees terminals the filesystem settings the SQLite database
Key idea

An environment (in code: ExecutionEnvironment) is one running Ryco server, identified by a stable environmentId. “Remote” is not a different kind of thing — it’s the same server reached over a network instead of over loopback. The runtime is never split; only the connection path changes.

Once you internalize that, the rest falls out:

  • Providers belong to the environment. A remote environment shows the remote machine’s Codex/Claude/etc., with the remote machine’s auth. (§15)
  • Projects, worktrees and chats belong to the environment. They live in that server’s SQLite DB and on that server’s disk — not on the client, and not inside the git worktree folder. (§16)
  • Choosing an environment is a per-thread decision, made when you compose a new chat — not a global switch and not tied to a worktree. (§6)
  • Two independent questions govern reaching a remote server: how do I connect to it (access) and how did it come to exist (launch). Kept deliberately separate. (§9)

05What an environment is — and where “saved environments” live

The primary environment is the local server the app was served from (the desktop shell starts one; the CLI is one). Saved environments are remote servers you’ve paired with. They connect concurrently — Ryco keeps every saved environment live in the background, not one-at-a-time.

The identity a server hands out

Every server exposes a descriptor at GET /.well-known/ryco/environment:

ExecutionEnvironmentDescriptor {
  environmentId,                 // stable UUID, persisted server-side
  label,
  platform: { os, arch },        // darwin|linux|windows · arm64|x64
  serverVersion,                 // used for the version-skew banner
  capabilities: { repositoryIdentity }
}

Where saved environments are stored (client-side only)

WhatHosted web app (browser)Desktop (Electron)
Registry of saved serverslocalStorage key ryco:saved-environment-registry:v1Electron main-process store via desktopBridge
Bearer token (the secret)Inside that same localStorage doc, 7-day sliding TTL, cleartextOS keychain, kept out of the registry
Client settingslocalStorage key ryco:client-settings:v1desktop bridge
Security note

In the pure-browser deployment, a remote environment’s bearer token sits in localStorage in cleartext with a 7-day expiry. The desktop app keeps it in the OS keychain instead. Treat pairing links and tokens like passwords.

The server never stores your list of environments — “saved environments” are purely a client concept. The connection state machine per environment is connecting → connected → disconnected → error, with a parallel auth state authenticated / requires-auth / unknown.

Under the hood — connection runtime specifics
  • Live connections held in a module-level Map<EnvironmentId, EnvironmentConnection> (service.ts). Each has its own WsRpcClient and subscription set.
  • Saved environments connect with concurrency 2 and a 2.5 s delay after the primary’s first shell snapshot, so the local env boots first.
  • WS auth handshake: HTTP bearer → POST /api/auth/ws-token → append ?wsToken=<short-lived> to the socket URL.
  • A 401 clears the stored token and asks you to pair again (for SSH environments it silently re-issues a bearer and retries).
  • Contracts: EnvironmentId, ExecutionEnvironmentDescriptor, ScopedProjectRef, ScopedThreadRef in packages/contracts/src/environment.ts. (There is no AccessEndpoint type — the endpoint contract is AdvertisedEndpoint.)

06When & where you choose an environment — the granularity question

Answering your question directly

Choosing an environment is per-thread. You pick it in the composer while the chat is still a draft (before the first message). It is not a global setting, and it is not per-worktree.

Mechanically:

Every project & thread is environment-scoped.

State is partitioned by environment, and each project/thread is addressed by a scoped ref: (environmentId, localId). The key format is literally ${environmentId}:${localId}.

The environment rides in the URL.

The chat route is /_chat/$environmentId/$threadId. “The environment I’m looking at” = the environment of the thread in the URL.

You choose it per-draft in the composer.

The branch toolbar’s “Run on” selector re-points the draft at the same logical project’s copy on the chosen environment. The choice is stored on the draft.

It locks after the first send.

Once a thread has any message or a live session, envLocked becomes true and the selector degrades to a static label. A committed thread cannot change environments.

The picker only appears when it’s meaningful.

It renders only when the same repository exists on more than one connected environment — i.e. you have a local clone and a remote clone of the same repo. Otherwise there’s nothing to choose.

Easy to misread

There is a store.activeEnvironmentId, but it is not a global “current environment” switch — it just tracks the primary/home server (used to know when the home env has finished bootstrapping). The real per-thread environment lives in the scoped refs, the URL, and the composer draft.

07The branch toolbar — two axes people conflate

The README calls it a “local/worktree environment selector,” which blurs together two independent choices that happen to share one toolbar. Keeping them apart is the key to the whole mental model.

Axis A · which server

“Run on”: This device / Cloud

Picks the environment (EnvironmentId) — your local server vs. a remote/paired one. This is the §6 per-thread choice. Icons: monitor = this device, cloud = remote.

Axis B · which checkout

Local vs. worktree

Picks EnvMode = "local" | "worktree" — whether the branch runs in the project’s main working copy or in an isolated git worktree. Nothing to do with which server.

So: is environment tied to worktree?

No. “Which server” (Axis A) and “local vs. worktree” (Axis B) are orthogonal per-draft settings. You can run on the local device in a worktree, on a remote device in the main copy, or any combination.

Under the hood — toolbar components
  • BranchToolbar.tsx composes BranchToolbarEnvironmentSelector (Axis A) + terminal toggle + BranchToolbarBranchSelector (Axis B).
  • Axis A options come from logicalProjectEnvironments — one entry per environment that has the active project’s logical repo. Renders only when there’s more than one.
  • Axis B: EnvMode resolved by resolveEffectiveEnvMode; stored per-draft as DraftSessionState.envMode.

When you add via a pairing URL, the client resolves the target, fetches the descriptor from /.well-known/ryco/environment, bootstraps a bearer token via POST /api/auth/bootstrap/bearer, persists the record + secret, and connects immediately. The deep-link route /pair is the entry point for hosted pairing links.

There is no “move this chat to another environment”

You add and remove servers, and you choose an environment for a new thread. But an existing thread is pinned to its environment for life — see §17 for why, and what that means for “keeping chats”.

09Access vs. launch — the two questions

Reaching a remote environment is two separate concerns. Keeping them apart is why SSH, Tailscale and a plain hosted server all reuse one model instead of each being a special case.

Access · “how do I connect?”

How the client speaks WS to the server

1 · Direct ws/wss (LAN IP or public HTTPS)
2 · Tunnelled (a Tailscale endpoint)
3 · Desktop-managed SSH port-forward → a local ws://127.0.0.1:PORT

Launch · “how does it exist?”

How the server came to be running

1 · Pre-existing (someone already ran it)
2 · ryco serve headless
3 · Desktop bootstraps it over SSH

They combine freely: a manually-hosted server reached by direct wss; the same server also reachable via Tailscale; an SSH-launched server reached through a forwarded socket; a local server published to your phone via a tunnel. In every case the ExecutionEnvironment is the same kind of thing — only the launch/access paths differ.

Why it matters

Because access and launch are separate, Tailscale is just an “endpoint provider” add-on and SSH is just a launch+forward helper — neither becomes a new environment type, and neither changes the protocol the renderer speaks. The final hop is always plain WebSocket.

10Network access & advertised endpoints

By default a desktop backend binds to loopback only. To reach it from another device you flip Settings → Connections → Network access.

Toggle sets a persisted mode.

serverExposureMode: "local-only" | "network-accessible" (default local-only).

The app relaunches.

There is no hot re-bind. The desktop app relaunches and re-spawns the backend with host = 0.0.0.0 (all interfaces) instead of 127.0.0.1. If no usable LAN address exists it refuses with “No reachable network address is available.”

Endpoints are enumerated.

The LAN IP is found by walking os.networkInterfaces() for the first non-internal IPv4 (skipping 127.* / 169.254.*). The result is surfaced as AdvertisedEndpoint records.

You pair another device.

“Create Link” generates a pairing link/QR from the chosen default endpoint.

What an advertised endpoint carries

Endpoints come from four hard-coded “providers” — server-core, desktop-core, manual, and the tailscale add-on — and are ranked client-side. Each is tagged:

FacetValues
reachabilityloopback · lan · private-network · public
provider.kindcore · private-network · tunnel · manual  (isAddon flags add-ons like Tailscale)
compatibility.hostedHttpsAppcompatible · mixed-content-blocked · requires-configuration · unknown
statusavailable · unavailable · unknown

Any http: endpoint is auto-tagged mixed-content-blocked — a browser on an HTTPS page (like app.ryco.dev) can’t open a plain http:///ws:// backend. That’s why LAN endpoints pair from the desktop/CLI directly, while HTTPS endpoints work from the hosted app.

Default endpoint & why it survives IP changes

The UI shows one default endpoint (it drives the QR + primary copy action) and hides the rest behind a +N expander. Your override is persisted by a stable endpoint kind, never the raw URL:

desktop-lan / server-network  →  "desktop-core:lan:http"
tailscale-ip                  →  "tailscale:ip:http"
tailscale-magicdns            →  "tailscale:magicdns:https"

So choosing “the LAN endpoint” keeps working after your 192.168.x.y changes when you switch networks — the stored key is the kind, not the address.

11Tailscale

Tailscale is the first (and currently only) endpoint-provider add-on. It contributes private-network endpoints for the same environment and pairing model — it is not a separate remote path.

What it discovers

The packages/tailscale wrapper shells out to exactly one status command and parses it:

tailscale status --json     // reads Self.DNSName + Self.TailscaleIPs
  • Tailnet IP — validated against the CGNAT range 100.64.0.0/10 (that’s the 100.x.y.z address).
  • MagicDNS name — Self.DNSName with the trailing dot stripped.
  • HTTPS MagicDNS URL — https://machine.tailnet.ts.net/ (a :port is only appended when it isn’t 443).

The desktop caches the MagicDNS name for 60 s; the status call times out at 1.5 s.

Tailscale Serve (HTTPS)

With --tailscale-serve the server sets up a scoped resource that runs:

tailscale serve --bg --https=443 http://127.0.0.1:<localPort>   // setup
tailscale serve --https=443 off                                // teardown on shutdown

Tailscale terminates HTTPS on the tailnet and reverse-proxies to the local backend, advertising the clean https://machine.tailnet.ts.net/. Use --tailscale-serve-port 8443 for a non-default port. If the serve command fails, it’s logged and swallowed — the server still starts.

Why the HTTPS row starts disabled (the “Setup” button)

The Tailscale HTTPS endpoint is shown but disabled until Ryco proves it reaches this backend: it does an HTTP GET of <magicdns-url>/.well-known/ryco/environment (2.5 s timeout) and only marks it available on a 2xx. Clicking Setup enables Serve (a relaunch, same as the CLI flag), after which the probe passes and the endpoint becomes usable — and hosted-app compatible.

Good to know

For https://app.ryco.dev, prefer an HTTPS Tailnet endpoint. A plain http://100.x.y.z:3773 works from a desktop client or an HTTP browser page, but not from the hosted HTTPS app (mixed-content). The commands tailscale ip -4 / tailscale cert appear only in the README examples — the code path gets everything from tailscale status --json and lets tailscale serve handle certs.

12Pairing, auth & sessions

The remote device doesn’t need a long-lived secret up front. It exchanges a one-time token for a session, then rides on the session.

A one-time token is issued.

ryco serve mints a one-time owner token: 12 characters, Crockford alphabet, 5-minute TTL. (The ryco auth pairing create CLI issues client-role tokens.)

The device exchanges it.

POST /api/auth/bootstrap → sets an HttpOnly session cookie, or POST /api/auth/bootstrap/bearer → returns a bearer sessionToken in JSON (used by non-cookie clients: SSH bridge, headless). Consumption is single-use, enforced by an atomic SQL update.

A session is created.

The session token is self-describing — base64url(claims).hmac signed with a server key — with a 30-day TTL. The token itself isn’t stored; only a DB row (for revocation) and the signing key are.

Each WS upgrade uses a throwaway token.

The long-lived cookie/bearer is exchanged via POST /api/auth/ws-token for a 5-minute WebSocket token appended as ?wsToken= on the upgrade URL. The upgrade also checks the request origin.

Managing access — the ryco auth CLI

CommandDoes
ryco auth pairing createIssue a one-time client pairing token (--ttl --label --base-url --json)
ryco auth pairing list / revoke <id>List active pairing links / revoke one
ryco auth session issueMint a bearer session (--role owner|client --ttl --token-only)
ryco auth session list / revoke <id>Inspect / revoke active sessions

Revocation always works even though session tokens are self-describing: verify re-checks the DB row and rejects anything revoked. Roles are enforced per-RPC — owner-only methods (network-access management, pairing management) fail for client sessions.

Hosted web pairing & the URL hash

A hosted link looks like:

https://app.ryco.dev/pair?host=https://backend.example.com:3773#token=PAIRCODE

The host is a query param; the token is in the URL hash. That’s deliberate — URL fragments are never sent in HTTP requests, so the pairing token never reaches the hosted app’s server (no logs, no Referer). The browser then connects directly to the backend; the hosted app never proxies traffic. Hosted pairing only works against HTTPS/WSS backends.

Under the hood — auth internals
  • Two services: AuthControlPlane (local, behind the ryco auth CLI) and ServerAuth (request-facing HTTP/WS).
  • Tables: auth_pairing_links (credential stored plaintext — single-use + TTL mitigate) and auth_sessions (+ client metadata, last_connected_at).
  • Signing key: file secret at <stateDir>/secrets/server-signing-key.bin, dir 0700 / file 0600.
  • WS enforcement has three layers: origin check + wsToken on upgrade → 5-min WS token issue/verify → per-RPC role gating.
  • unsafe-no-auth exists as an explicit escape hatch, not a normal mode.

13Headless ryco serve

Run a server with no GUI — e.g. on a box you reach over SSH:

npx ryco serve --host "$(tailscale ip -4)"
npx ryco serve --tailscale-serve                 # opt in to HTTPS MagicDNS (port 443)
npx ryco serve --tailscale-serve --tailscale-serve-port 8443

It starts the server without opening a browser and prints a connection string, an owner pairing token, a pairing URL, and a terminal QR code:

Ryco server is ready.
Connection string: http://<host>:3773
Token: <PAIRCODE>
Pairing URL: http://<host>:3773/pair#token=<PAIRCODE>

  ▄▄▄▄▄▄▄  ▄▄ ▄ ▄▄▄▄▄▄▄        # QR of the pairing URL (half-block glyphs)
  █ ▀▀▀ █  ▄▀▄  █ ▀▀▀ █
  ...

From another device you then: scan the QR, enter the full pairing URL in the desktop app, enter host + token separately, or (for HTTPS backends) open the hosted pairing URL. Shared flags include --host, --port (default 3773), a cwd positional, plus the Tailscale flags; every flag has an RYCO_* env equivalent.

Current limitation

The GUIs don’t yet support adding projects on remote environments. On the server machine, use ryco project … for now. Full GUI remote project management is “coming soon.”

14Desktop-managed SSH launch

When you want the desktop app to start (or reuse) Ryco on another machine over SSH: Settings → Connections → Add environment → SSH, enter e.g. user@host, confirm. The desktop main process owns this because it needs to spawn SSH, handle password prompts, and clean up forwards.

Resolve the target.

ssh -G <alias> parses hostname/user/port (falls back to alias-as-hostname).

Reuse a live tunnel if healthy.

An existing forward is probed for 2 s; reused if healthy, rebuilt if stale.

Launch or reuse the remote server.

Pipes a POSIX script over SSH. It keeps per-target state in ~/.ryco/ssh-launch/<key>/, resolves Node (activating fnm for non-interactive shells), then runs node <script> / ryco / npx --yes ryco@latest. A pre-existing default server is reused as external; otherwise it starts a managed one: serve --host 127.0.0.1 --port <picked> --base-dir ~/.ryco (port scans from 3773).

Open a local port-forward.

ssh -o ExitOnForwardFailure=yes -o ServerAliveInterval=15 -N -L <localPort>:127.0.0.1:<remotePort>. The renderer then connects to ws://127.0.0.1:<localPort> — an ordinary WebSocket, like any other environment.

Pair over the forward.

Issues a token on the remote (auth pairing create --json), exchanges it for a bearer over loopback, fetches the descriptor, and saves the environment.

Password prompts & reconnect

SSH auth uses an askpass helper fed by the secret you type in the renderer (a modal with a 3-minute timeout); up to 2 retries. No credentials are stored beyond the session. On reconnect, Ryco restores the SSH bridge first (re-runs the launch/forward, refreshing the local URLs) and only then reconnects the WebSocket.

What’s saved for an SSH environment is just the target — desktopSsh { alias, hostname, username, port } — plus the loopback base URLs, label and timestamps. The transient remote port and pairing token are not persisted; they’re re-derived on each reconnect.

15Providers on an environment — and “not installed on the remote machine”

Providers (Codex, Claude, Copilot, OpenCode, Cursor) run on the server’s machine. This is the crux of your question.

Answering your question directly

If a provider isn’t installed on the remote machine, Ryco does not provide it and does not ship credentials across. When you connect to a remote environment, the providers/versions/auth you see are the remote machine’s. To use one there you must install and login its CLI on that machine (over SSH/terminal). Syncing provider auth across machines is an explicit non-goal.

How Ryco detects availability

Each provider is probed by literally running its CLI/SDK on the host. The result flows to Settings → Providers as a live status snapshot (installed, version, status, auth, models…):

ProviderProbeIf missing / unauthenticated → message
Codexspawn codex app-server, initialize + account/read“Codex CLI (codex) is not installed or not on PATH.” · “Run codex login…”
Claudeclaude --version + an Agent-SDK capability probe“Claude Agent CLI (claude) is not installed or not on PATH.”
Copilot@github/copilot-sdk getStatus/getAuthStatus“GitHub Copilot CLI (copilot) is not installed or not on PATH.”
OpenCodeopencode --version (min 1.14.19), then connect“OpenCode CLI (opencode) is not installed or not on PATH.”
Cursoragent about (version + auth in one call)“Cursor Agent CLI (agent) is not installed or not on PATH.” · “Run agent login…”

A missing provider stays a live instance but reports installed: false with the exact remediation message — a red row you can read, not a silent failure. (A driver the build doesn’t even know about shows up as a separate unavailable shell.) Ryco has no in-app login for coding-agent providers; it reflects the CLI’s own credential store on that host.

Provider instances — running the same driver twice

Routing is instance-based. A driver is the implementation; an instance (ProviderInstanceId like codex_work) is a named copy with its own config. ServerSettings.providerInstances stores per instance:

driverdisplayNameaccentColorenabledenvironment (env vars)driver-specific config

Instances hot-reload when settings change. This is how you run codex_personal + codex_work with independent auth, models and colors.

Finding binaries on a remote/GUI machine

Each instance’s binaryPath defaults to the bare command (codex, claude…) resolved against PATH, but accepts an absolute path — the per-instance “point at a custom binary” knob. Crucially, a fixPath step at server boot rehydrates PATH from your login shell, so a desktop- or SSH-launched server still finds tools under Homebrew, nvm, ~/.local/bin, etc. Per-instance env vars carry auth identity (ANTHROPIC_API_KEY, OPENAI_API_KEY…), and there are dedicated home-isolation knobs (CODEX_HOME/shadow home, a custom Claude HOME, OpenCode serverUrl).

Ryco can update (not install) a provider remotely

server.updateProvider infers how the CLI was installed (npm / bun / pnpm / brew / native) and runs the upgrade on the server machine, streaming progress back. Latest-version advisories come from the npm registry (1-hour cache). But first-time install and login remain yours to do on that host.

Status buckets (idle / in_progress / review / done) are a per-thread field (manual_status_bucket), not a worktree property. RepositoryIdentity — derived from the git remote URL — is used only for grouping local and remote clones of the same repo in the sidebar; it never routes anything. Symlinked roots (Dropbox ↔ CloudStorage) canonicalize to the same identity via git rev-parse --show-toplevel. “Local project folders” are purely client-side UI state, not in the DB.

17Copying a worktree to “keep the chats”

The direct answer

You cannot copy a worktree directory to another environment and keep its chats. Copying the folder carries the git checkout and nothing else. There is no thread copy / move / transfer / export / import feature anywhere in Ryco — an exhaustive search turns up zero.

Why, concretely:

  • Chats aren’t in the folder. Messages/activities/events are rows in the server’s state.sqlite, keyed by thread_id. The worktree directory is a plain git checkout under ~/.ryco/worktrees/… — it contains none of them.
  • A thread only points at a worktree via a worktree_id FK (or a legacy worktree_path string). Copying the directory creates no DB rows and rewrites no pointers, so the destination’s database has nothing referencing it.
  • Environments are a hard wall. Each server has its own state.sqlite and environment-id; threads are addressed as (environmentId, threadId). Environment B’s DB simply has no rows for environment A’s threads, and there’s no ingestion path to add them.
What you’d actually have to do

To carry chats to another machine you’d have to copy the whole state.sqlite (or replay its event log) and reconcile the workspace_root paths — there is no supported, first-class flow for that today.

Lifecycle facts worth knowing

  • Chats are pinned to a stable thread_id, not to a path — so renaming/moving the checkout doesn’t lose them.
  • Archiving a worktree leaves its threads fully intact.
  • Deleting a worktree cascade-deletes its attached threads (soft-delete; the underlying events remain). So a hard delete intentionally removes those chats.
  • A real thread.attach-to-worktree command exists, but it only runs as an internal step of worktree create/import — there’s no user-facing “reassign this chat” button, and nothing crosses environments.

18Keeping up to date

“Up to date” means four different things in Ryco. Here’s each, and who’s responsible.

Desktop app auto-update

Via electron-updater against GitHub Releases, on two channels (latest / nightly). Downloads and installs are always user-triggered — never silent (autoDownload=false, autoInstallOnAppQuit=false). It checks 15 s after start and every 4 h, and drives the sidebar pill: Update available → Downloading (x%) → Restart to update. Only packaged production builds (Linux: AppImage) update.

Client ↔ server version skew

Advisory only — no negotiation

The WS upgrade is auth-only; nothing rejects or downgrades on version. The client compares its version to the server’s serverVersion and, if they differ, shows a dismissible banner (“Try syncing the client and server to the same Ryco version”). If the two schemas stay wire-compatible everything works; if a payload shape is incompatible you get a decode error, not a graceful fallback.

Updating a remote / headless server

There is no server self-update. A plain npx ryco serve pulls the latest published version only on relaunch. An SSH-launched managed server is reused while healthy — a version bump alone won’t restart it, so a long-lived managed server keeps its old version until you stop it (then the next connect relaunches via ryco@latest). A pre-existing external server is never managed or restarted by Ryco.

Reconnect, liveness & freshness (automatic)

  • Heartbeat ping/pong; isHeartbeatFresh uses a 15 s window.
  • Exponential backoff 1 s → 64 s over 7 retries (8 attempts), at both the socket and subscription layers.
  • Browser-resume reconnect on tab focus/visibility for any stale connection.
  • SSH bridge restored first, then the WebSocket, on reconnect of an SSH environment.
  • Bootstrap gate: after every (re)connect the environment isn’t “ready” until a fresh shell snapshot arrives; all subscription streams (shell, thread, config, lifecycle, VCS, terminal, auth) re-emit their snapshots so the UI re-syncs.
  • All saved environments are kept connected and fresh in the background (concurrency 2), not just the active one; removed ones are torn down.

Provider CLIs

Ryco surfaces an npm-registry “behind latest” advisory (1-hour cache) and offers one-click server.updateProvider where the provider supports it — running on whichever machine hosts that server. Providers without an update capability, and all first-time installs/logins, are the user’s responsibility on that host.

20Limitations & “coming soon”

  • No GUI remote project management yet. Add projects on a remote environment with ryco project … on the server; full GUI support is planned.
  • No thread move/copy/transfer across worktrees, projects, or environments (§14).
  • No client↔server version negotiation. Skew is advisory; incompatible payloads fail to decode.
  • Endpoint “providers” are a data convention, not a plugin registry. tunnel is in the schema but not implemented; Tailscale is currently desktop-only as an endpoint provider.
  • No live re-bind. Toggling network access or Tailscale Serve always relaunches the desktop app.
  • Managed remote servers don’t auto-upgrade on reuse — restart them to pick up a new version.
  • Pairing credentials are stored plaintext in auth_pairing_links (single-use + short TTL mitigate); session tokens aren’t stored (HMAC + DB revocation).
