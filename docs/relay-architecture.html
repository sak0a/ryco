Ryco relay architecture

One Hub. Every Ryco surface.

See how clients reach node-owned work through a bounded, trusted relay.

Walk through the flow Inspect the trust boundary

Transport uses HTTPS and WSS. Payloads are additionally encrypted between the client and the far end of the channel it was routed to, on channels that negotiate it. What that is worth differs in kind rather than in degree. In the signed Ryco mobile app, on a channel resolved to a node identity the owner verified and pinned, the Hub's remaining view is traffic metadata — who talks to which node, when, and how much. In the browser the Hub also serves every byte of the page's code, and the page pins no node identity, so the Hub can be the far end of that channel or serve code that copies the payload: payload confidentiality against the operator is not claimed for that tier at all.

Role and capability lens

A role is not a route.

Every human needs a grant to the selected node. Account role only sets the upper bound after that grant exists.

effective role = min(account role, node grant)

Trusted relay boundary

HTTPS and WSS protect transport, and on a channel that negotiated payload encryption the Hub forwards ciphertext rather than readable bytes. What that is worth depends on the client. The Ryco mobile app runs a signed tier whose code is distributed independently of the Hub; it reaches the stronger guarantee on channels it resolves to a node identity the owner verified and pinned through the pairing comparison on that install. Those pins are install-scoped, and an app reinstall, an OS restore, a device transfer, or a secure-store reset destroys every one of them at once and returns the device to first contact until the owner re-pairs. The browser runs an unsigned tier whose ceiling is structural for two independent reasons. It pins no node identity, so it cannot tell whether the far end of the channel is the owner's machine or the Hub standing in for it — and that one needs no substituted code at all. Separately, the Hub serves every byte of that page's code, so it could serve code that completes the same handshake and copies the payload anyway. On a channel that negotiated no encryption the Hub forwards readable bytes transiently and policy forbids logging or persisting them. On every channel, encrypted or not, the Hub still sees which account and session talk to which node, channel open and close events, frame sizes and timing, the capability and role it issued, heartbeats, and transfer accounting.

Failure and recovery

Fresh state wins.

Recovery never lets a stale connection publish readiness, role, snapshots, or mutation authority.

Hosted client resumes after suspension
  1. Revalidate the human session.
  2. Re-read the authorized node directory.
  3. Request a fresh single-use ticket.
  4. Create a fresh relay attempt.
  5. Accept a current shell snapshot.
  6. Publish readiness and mutation authority.
Node or Hub transport disconnects

Work remains local. The node discards the old generation, requests a fresh proof challenge, and reconnects through bounded backoff. It never reuses a proof frame.

A grant or node is revoked

The Hub closes affected access, denies new tickets, and returns current directory state. Existing clients must rebuild authority before any later mutation.
