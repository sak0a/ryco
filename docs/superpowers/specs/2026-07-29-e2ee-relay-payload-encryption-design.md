# End-to-end relay payload encryption design

## Problem

Relayed application payloads are confidential today only by operator policy. The relay
protocol's `data.payload` is an opaque byte string, but the bytes inside it are plaintext RPC
JSON: the relay operator (the Hub, in the sense [relay-protocol.md](../../relay-protocol.md)
already uses) decodes every relay frame, enforces sequencing and budgets, and forwards the
payload while promising never to read, log, or persist it. Nothing cryptographic enforces that
promise. A passive compromise, an accidental persistence bug, or a compelled operator exposes
payload bytes. Separately, nothing in the relay protocol lets a node distinguish a genuine
client from a session the relay operator originated itself, because tickets and `channel.open`
authority are operator-authored.

This design makes relayed payloads AEAD ciphertext end to end between a client and its node,
and — on the signed native tier, after mutual owner verification — makes operator origination
of either endpoint detectable and rejected.

## Scope

The E2EE layer lives entirely inside the relay `data.payload`, beneath the relay frame schema
and above the application RPC JSON — exactly the evolution the relay protocol reserves
("Keeping the payload schema opaque allows later application-level end-to-end encryption
without changing relay routing"). Consequences, all deliberate:

- **Zero relay contract or schema changes.** No new frame type, close reason, limit,
  capability literal, or protocol version. An E2EE channel is an ordinary relay protocol 1.2
  channel; the relay contract fixture corpus (`packages/contracts/fixtures/relay/v1`) is
  untouched. A conforming relay needs no data-plane change at all.
- **Module home**: the shared reference implementation lands in `packages/shared`, beside
  `packages/shared/src/relayMessageChunks.ts`, whose chunking pipeline the envelope slots into.
  E2EE fixtures live in their own directory, `packages/shared/fixtures/e2ee/v1/`, generated by
  a dedicated script following the existing fixture-generator convention.
- **Canonical specification**: [docs/relay-e2ee-protocol.md](../../relay-e2ee-protocol.md) is
  the normative wire specification — byte layouts, constants, registries, state machines,
  transcripts, error taxonomy, bounds, and the normative test-vector enumeration. This design
  document summarizes the decisions and defers to the spec everywhere; where the two disagree,
  the spec governs.

Out of scope for version 1 (each listed with rationale in the spec): operator-proof web E2EE,
encrypted history mirroring, multi-party channels, post-quantum suites, key escrow,
hardware-bound agreement keys, post-compromise recovery within an open channel, and
multi-device client-key introduction.

## Design summary

Send side: RPC bytes get a fixed inner-record type prefix, are AEAD-encrypted, and are wrapped
in an E2EE envelope whose first post-strip byte discriminates it from legacy JSON and from
negotiation records; the envelope then flows through the unchanged chunking pipeline
(`prepareRelayMessage`), keeping the chunk-capability prelude and `0x00` chunk magic behavior
exactly as today. Receive side discriminates only after chunk reassembly and prelude stripping;
unauthenticated bytes never reach the RPC parser. A per-channel mode machine
(negotiating / e2ee / legacy) makes malformed or unknown first bytes fatal in every state,
forbids mid-channel upgrades, and makes plaintext-after-E2EE and negotiation-after-legacy-lock
channel-fatal.

The handshake is one round trip of Noise (IK for signed native, NX for web) carried in
negotiation records after `channel.accept`, bound to an endpoint-constructed authorization
context, confirmed by a keyed confirmation tag, and sealed by a session-binding hash that
becomes part of every record's AAD. Records are protected per direction with epoch/counter
nonces, a domain-separated HKDF rekey ratchet, strict receiver-state sequencing, and an
authenticated close exchange. Size caps apply to the encrypted bytes; each endpoint derives a
per-channel plaintext ceiling from the negotiated effective message ceiling
(`min(RELAY_MAX_RPC_MESSAGE_BYTES, maxQueuedBytes − maxControlFrameBytes)`) minus the published
envelope overhead constant, enforced pre-encryption with its own sender-local error.

## Key decisions

**Client-selected single suite.** Version 1 registers exactly one suite
(`Noise_IK_25519_ChaChaPoly_SHA256` / `Noise_NX_25519_ChaChaPoly_SHA256`; the tier selects the
pattern). The client verifies the node's signed ordered suite list, intersects local policy,
deterministically selects, and builds its first Noise message for that suite; the server may
only accept or reject. Rationale: a one-round-trip IK/NX exchange has no room for
server-driven renegotiation, and server selection plus retry is a classic downgrade surface.
Suite-list stripping is detected because the exact hello wire bytes are bound into
confirmation. Multi-suite negotiation requires its own reviewed handshake revision.

**IK for signed native, NX for web — tiered honest guarantees.** Native mobile holds a
hardware-backed device identity key and can therefore run Noise IK with a cross-signed static
agreement key, giving mutual authentication. Web deliberately has no durable client identity
(the hosted-client policy keeps auth material out of every browser storage surface), so it
runs NX: the node authenticates to the web client, never the reverse. The spec states
guarantees strictly per tier and per policy: passive and retroactive protection on every E2EE
channel; active-operator protection only on the mutually verified signed native tier; and the
web tier is **never operator-proof**, because the operator serves the web code and can
exfiltrate plaintext while completing a genuine handshake. The spec's threat model reproduces
the retained-metadata visibility list (who talks to which node, open/close events and reasons,
frame sizes and timing, `channel.open` authority fields, heartbeats, transfer accounting) so
no reader mistakes payload encryption for traffic privacy.

**Capability advertisement over a proven legacy-safe carrier — never probe.** An E2EE-capable
node advertises with a signed capability statement (identity, prekey certificate, suite
registry, continuity chain, admission policy, monotonic policy generation, bounded validity)
carried in a single reserved-tag JSON object sent as the first node-to-client payload. The
carrier's legacy safety is not assumed: the spec fixes six normative compatibility cases
(chunk-assembler pass-through, protocol-socket routing, dispatcher ignore, wrapper
pass-through, the prohibited client-to-node direction, prelude whitespace tolerance) verified
against the pinned current client and node parsers, each backed by a required fixture family.
The carrier must fit one unchunked payload with full prelude headroom; a node that cannot fit
it never truncates — it closes under effective `requireE2EE`, otherwise it counts a fallback
occurrence and stays legacy.

**Latch + `requireE2EE` + `requireApprovedClientE2EE`.** Downgrade resistance is layered.
Clients latch E2EE per node identity fingerprint (never the operator-minted `nodeId`) once
capability evidence chains to a verified pin; a latched client never silently falls back.
Native persists the latch durably; web holds it in memory for the app session only and the
disclosure text says so. Node-side, `requireE2EE` (default off at introduction) rejects
plaintext but still admits unsigned web NX, so it closes the plaintext downgrade path without
any whole-node claim; `requireApprovedClientE2EE` implies effective `requireE2EE`, admits only
approved signed native IK clients, and is the only policy supporting a whole-node
active-operator guarantee — at the deliberate cost of disabling web and legacy access, with
mandatory operator lockout warnings and restart/recovery semantics that never silently weaken
the effective policy.

**Node-side client authorization (the Branch A record set).** The node keeps owner-approved
client identity fingerprints keyed by `(hubOrigin, accountId, fingerprint)` with status,
maximum role, and capability set. Unknown or pending keys never hold a live channel; a
first-seen key gets only a bounded pairing exchange (safety-number display, no application
payload) and approval takes effect only on a fresh ticket/channel/handshake. Bounded caps,
retention, and deterministic eviction guarantee an unapproved flood can never evict approved
or revoked security state; revocation closes matching active channels before acknowledgment.
This — paired with the client's owner-verified node pin — is what makes the active-operator
guarantee true on the signed tier, because operator-authored `channel.open` authority is
capped by the node-local record rather than trusted.

**Identity-continuity certificates instead of re-verify prompts.** Legitimate node identity
rotation must not raise the same warning as real substitution, or owners learn to dismiss it.
The outgoing identity key signs a continuity certificate (bounded, ordered, monotonic
generation, keyed to a stable node-local continuity id) carried in the capability
advertisement; a pinned client verifying the complete chain updates its pin silently, while a
missing, spliced, reordered, truncated, or invalid chain is channel-fatal and surfaces
re-verification. Lost-key recovery deliberately breaks the chain and is never synthesized.

**First-party Noise state machine on audited noble primitives — a resolved, recorded
deviation.** The original library policy required an audited full Noise implementation and
made its absence a hard stop. That stop condition fired: the survey found no pure-TS/JS Noise
implementation ever audited as a Noise implementation, none exposing a supported
exporter/post-`Split()` API, and none covering IK+NX on Bun, browsers, and Hermes (details
under Alternatives). The owner accepted a bounded deviation, recorded verbatim in the spec: a
first-party minimal frozen Noise IK+NX state machine in `packages/shared`, performing no
primitive arithmetic of its own, on independently audited `@noble/curves`, `@noble/ciphers`,
and `@noble/hashes` pinned within their audited lineage. Normative mitigations: official
cacophony/snow Noise vectors must pass; cross-implementation vector tests against an
independent Noise implementation; property-based state-machine tests; the full adversarial
suite against an attacker-controlled relay harness; and a scoped third-party audit of the
state-machine module is required before any release flips the `requireE2EE` default. Until
that audit the residual risk is carried openly in the spec's security-considerations list.
Mandated primitive behavior is pinned too: strict RFC 8032 Ed25519 verification
(`zip215: false`), abort-on-zero-shared-secret X25519 as the single low-order behavior, full
P-256 point validation, and fail-closed React Native randomness via the `expo-crypto`
`getRandomValues` polyfill installed before any primitive import.

## Alternatives rejected

- **Probe-based discovery** (send an E2EE hello and see what happens) — destructive. A legacy
  node fails to parse the hello and deliberately fails the session, closing the channel and
  burning a single-use ticket per attempt against the ticket rate limit. Discovery is
  advertisement-only, and a client with no validated evidence never sends a negotiation record.
- **New relay frame types** for negotiation or E2EE data — rejected by every current peer:
  unknown frame types are protocol errors for the relay and both endpoint runtimes, so this
  path forces a relay protocol version bump and a coordinated upgrade of relay and all peers,
  destroying the zero-contract-change property for no functional gain over in-payload framing.
- **New close reasons** — the relay close-reason set is closed; adding a literal cascades into
  a protocol-minor bump, contract fixture regeneration, and relay codec changes. Every
  E2EE-fatal condition instead maps onto existing close reasons, with a generic fixed-size
  pre-key reject and encrypted post-key error records so failures leak no oracle.
- **Existing JavaScript Noise libraries** — none qualifies, each for concrete reasons:
  `@chainsafe/libp2p-noise` is XX-only (IK was removed with Noise Pipes), has no third-party
  audit of its handshake logic despite a real history there (CVE-2022-24759, an unvalidated
  handshake-payload-signature MITM), ships WASM-assisted primitives, and is unusable outside
  the libp2p stack; Holepunch `noise-handshake` and emilbayes `noise-protocol` cover IK but
  sit on `sodium-universal` (native bindings on servers, unaudited JS fallback in browsers,
  nothing on Hermes) and are unaudited — and the latter is dormant with the wrong hash
  function; `@waku/noise` is the only genuinely pure-TS machine with the right suite but is a
  dormant 0.0.x release shipping neither IK nor NX; `@stablelib/*` primitives have no audit
  trail at all and are strictly dominated by noble. No JS Noise library exposes a supported
  exporter API, which the key schedule requires.
- **Hardware-bound (ECDH) agreement keys** — deferred. The existing device keys are sign-only
  as built; version 1 uses software X25519 agreement keys cross-signed by the identity keys,
  and the envelope's suite field keeps the hardware migration path open.

## Node relay seams

The node-side relay path carries no E2EE code. It carries the seams an E2EE layer will attach
to, and each one exists because the specification names a behavior the previous shape could not
express. They are listed here because a seam that cannot actually be driven is worse than none
— it reads as a solved problem — so each entry states what drives it.

- **Payload discrimination before the RPC decoder** (`makeRpcByteSession`, `interceptor`).
  Discrimination has to happen after chunk reassembly and prelude stripping (§4.3), and an
  authenticating layer has to be able to stop unauthenticated bytes from reaching the parser.
  With no interceptor installed, every payload decodes exactly as before. The interceptor
  deliberately has **no fatal disposition**: it runs on the session's consumer fiber, so a
  verdict returned from it could not reach the caller of `receive` for the payload that
  produced it. `RelayRpcChannelSession.receive` therefore stays a plain backpressure bit.
- **Channel context at open** (`RelayChannelSessionFactory.open`): channel id, the capability
  and effective role the peer named, the negotiated relay protocol major/minor (taken from the
  relay contract constants, since the connection accepts a `ready` naming exactly those), and
  the connection identity. Together these are §8.3 elements 1–4 and 13–14. The connection
  identity is passed as a **getter, read at each use**: the node id is assigned while the
  connection authenticates, and the first connect after enrollment approval routinely opens
  channels before that read completes. A captured value would leave such a channel without an
  identity for its whole lifetime, silently disabling E2EE on it.
- **An out-of-band send handle** sharing the channel's outbound sequence, chunk-support latch
  and refusal handling with the RPC path, so a negotiation record cannot run a second,
  competing sequence. It is all-or-nothing across the frames of one message
  (`RelaySendQueue.enqueueDataBatch`): a refusal produces no wire record at all, which is what
  §11.4 requires of `e2ee_send_unavailable`. It names **why** it refused —
  `message_too_large`, `peer_unsupported`, `queue_full`, `channel_closed`,
  `sequence_exhausted` — because §11.4 makes a size failure and unavailable transmission
  admission different errors with different remedies.
- **An acceptance announcement** (`onAccepted`), awaited before any inbound frame is
  delivered, so a carrier that must occupy outbound sequence 0 (§5.4) actually can. It may be
  asynchronous and is awaited; a failure closes the channel with `channel_rejected`, the same
  reason every other open-time rejection produces, because §11.5 requires pre-key fatal
  conditions to be externally indistinguishable.
- **A session-driven close naming its reason**, with the channel's queued data drained to the
  socket before the outer `channel.close` is enqueued. This is how §11.2, §11.3 and §10.3
  select a close reason and get a final record out ahead of the close: emit the record through
  the send handle, then call `close("channel_rejected")`. The drain is performed by the close
  path itself (`RelaySendQueue.flushChannel`), not by a notification the connection owner may
  defer, so the ordering does not depend on how the owner schedules flushes.

**The drain is best effort, and knowingly so.** A channel the peer has flow-paused cannot be
drained without violating the pause, and a socket that cannot take the bytes cannot be made to;
in both cases the queued record is discarded with the channel. This is exactly the relay
behavior §10.3 already assumes — queued data at close has no delivery guarantee — and it is why
the close machine takes its evidence from an encrypted peer proof rather than from a successful
enqueue.

### Declared behavior changes

Every change to existing behavior made while introducing these seams, including ones that are
plainly correct:

1. **A refused relay send no longer kills the RPC server fiber.** The byte session's sink used
   to `orDie`, so a full outbound queue became a defect that tore down the RPC server and every
   in-flight request on the channel. It is now a typed `RpcOutputRefusedError` that drops the
   one response and leaves the fiber running. This is required by §11.4 — backpressure MUST NOT
   be escalated to a channel-fatal condition — and it is correct without E2EE too: the registry
   already reacts to the refusal by closing the channel and naming the cause, so dying here
   punished unrelated requests for a condition that was already handled. Genuine sink defects
   remain defects. Observable difference with no interceptor installed: where a saturated
   outbound queue previously produced a fiber defect _and_ the registry's close, it now
   produces only the registry's close.
2. **A close no longer discards queued data before it can be written.** `closeChannel` drains
   the channel's outbound queue before enqueueing the `channel.close`. Previously the queue was
   purged first, so a message enqueued immediately before a close was destroyed even when the
   socket could have taken it.
3. **A peer-initiated `channel.close` explicitly does not drain.** The relay no longer knows
   the channel, so pushing its queued data would emit data frames for a channel that is gone.
4. **`onAccepted` failure closes with `channel_rejected`, not `internal_error`** (see above).
5. **A stale node id is cleared.** A post-authentication identity read reporting no active node
   now clears the cached id instead of leaving the previous enrollment's value in place.
6. **A socket write failure during the close drain is reported as `internal_error` rather than
   `network`.** The drain reports a failed write instead of throwing, so the connection failure
   surfaces through the subsequent control-frame refusal. Both classifications retry
   identically; only the recorded failure label differs, in a corner reachable only when the
   socket fails during a channel close.
7. **The relay protocol version the registry stamps on frames now comes from the relay contract
   constants** instead of a module-local literal. Same values today, by construction: the
   connection accepts no other `ready`.

### Carried forward to the record-protection phase

**§9.3 requires transmission admission for the entire record _before_ the `(epoch, counter)`
pair is assigned, and the send handle's refusal report does not by itself satisfy that.** The
handle reports a refusal after the caller has already produced the bytes it wanted to send. A
layer that encrypts under counter N, is refused, and rolls its counter back would reuse that
nonce with different plaintext — a catastrophic AEAD misuse, and precisely the failure §9.3's
ordering exists to prevent. The refusal report is what makes the correct behavior _possible_
(no wire record is produced, so nothing was consumed at the relay layer), not what implements
it. The record-protection phase MUST obtain admission first — reserving capacity for every
chunk of the encrypted record, whose size is known before encryption from the plaintext length
and the published envelope overhead — and only then assign the pair and invoke the AEAD, taking
`e2ee_send_unavailable` (§11.4) on refusal without consuming a pair. A sender that instead
encrypts first and rolls back on refusal is non-conforming even though every relay-layer
assertion in this phase still passes.

## Verification

Phase 0 ships no implementation code; the specification itself must pass a dedicated
independent adversarial protocol review before any implementation work begins. Implementation
phases then verify against the spec's normative enumeration:

- **Deterministic vector corpus** in `packages/shared/fixtures/e2ee/v1/`: fifteen families
  covering payload discrimination and the chunk pipeline, the six carrier compatibility cases,
  capability statements, prekey certificates, continuity chains, full IK and NX handshakes with
  every named intermediate, record protection and exact AAD bytes, rekey boundaries and
  exhaustion, every mode-machine transition row, authenticated close, error records,
  fingerprints, safety number and `WebSAS` rendering, and the official Noise core vectors.
  Fixtures are generated, never hand-edited, with a byte-for-byte drift test and conspicuously
  test-only key material.
- **Adversarial suite** against an attacker-controlled relay harness: key and suite-list
  substitution, tier/pattern confusion, reflection, transcript and context-commitment
  mismatch, role/capability escalation, node substitution, cross-account splice, replay,
  reorder, gap, truncation, counter and epoch-boundary abuse, downgrade strips against the
  latch and node policies, forged/replayed/rollback capability statements, and
  implicit-finish abuse.
- **Cross-runtime equality**: every family under the Node test gate; web-facing families in
  the browser test suite; the complete corpus on physical devices on both mobile platforms
  before the native client ships E2EE — a release-blocking acceptance gate, not an optional
  extra, because there is no continuous on-device rig.
- **Repository gates**: the public gate set (`bun install --frozen-lockfile`, formatting,
  lint, typecheck, Effect typecheck, `bun run test`, build) on every PR, plus the web browser
  suite for web-facing changes.

## Rollout

Rollout is phased and compatibility-first: shared module and vectors, then node, then native
mobile, then web, then hardening — with legacy interop preserved throughout and every phase
landing its own negative tests rather than deferring attack coverage to the end.

`requireE2EE` ships default-off. A later release may flip the default only when the operator
rollout criteria hold: both released client tiers speak E2EE in at least one shipped release
each; the authoritative durable node-side fallback counter records zero occurrences over a
full observation window of representative use (client diagnostics are corroborating only,
since a malicious relay can suppress them); and the scoped third-party audit of the handshake
state-machine module is complete. Operators may enable the policy earlier by explicit
configuration. `requireApprovedClientE2EE` is never enabled by that flip; it remains a
deliberate operator opt-in with a documented availability cost.

The final rollout tail — end-to-end owner acceptance against a live deployment — is gated on
separate operator rollout criteria outside this document. No compatibility downgrade, relay
protocol change, or new close-reason literal is permitted at any point.
